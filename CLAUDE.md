## Commands (npm, Node 22)

- `npm run build` — `tsc -b && vite build` → `dist/`. This is what Logseq loads; rebuild before every Reload.
- `npm run build:watch` — `vite build --watch` (no type-check); press Reload on the plugin card after each rebuild.
- `npm run lint` — oxlint (`.oxlintrc.json`: react + typescript + oxc plugins).
- `npm run typecheck` — `tsc -b` only (`tsconfig.app.json` covers `src/` **and** `tests/`).
- `npm test` — Vitest, every `tests/**/*.test.ts`, node environment.
- `npm run test:one -- tests/logseq/hostVersion.test.ts -t "parses"` — one file and/or one test name (verbose reporter).
- `npm run test:watch` — Vitest watch mode.
- `npm run dev` — plain Vite dev server. Logseq does not use it (no `devEntry`); it only helps to eyeball the React UI in a browser.
- **Dev loop in Logseq:** Settings → Advanced → Developer mode → `t p` → *Load unpacked plugin* → select the **repo root** (not `dist/`). After a rebuild, press Reload on the plugin card. To see plugin console output, launch Logseq as `/opt/logseq-desktop/Logseq --enable-logging 2>&1 | tee /tmp/logseq-console.log` and grep for `[gdsync]`.

## Target Environment (hard constraints)

- Logseq desktop **0.10.15** (file-based graphs; installed on this machine as `logseq-desktop-bin`). The host ships `@logseq/libs` **0.0.17**, so pin the SDK to that version. The TypeDoc site and npm `@next` (0.3.x) document methods this host does not implement.

## Architecture (see plan §3 for detail)

- **B (confirmed by M0):** the plugin runs with `effect: true` and does file I/O through the host's Electron bridge, `window.top.apis.doAction([...])`. That bridge is undocumented and unofficial but fully works on 0.10.15 (see `docs/spike-results.md` §2). The M5-C local-helper fallback is not needed.
- HTTP: one transport, iframe `fetch`, for OAuth and every Drive endpoint. `logseq.Request` is not used.
- Layering is strict:
  - `src/sync/` is pure TypeScript with no `logseq`/Google imports, and is unit-tested with in-memory fakes. M6: `state.ts` (`SyncState` = §3.5 `entries` **plus a persisted remote view `remote`**, `SyncJournal`, `createSyncStateStore(JsonStorage)`, `ensureDevice`, `graphKey(name, path)` — the state is keyed by the graph **path**), `remote.ts` (the `RemoteMirror` interface, the only thing the engine knows about Drive; `applyDeltaWithDuplicates`), `planner.ts` (`planSync` = §3.6 step 5 table; `conflictOps` = D7 answers → ops; `SyncOp` union incl. `update-base`, `drop-base`, `keep-both`, `trash-duplicate`), `executor.ts` (`executePlan`: pool, per-op `Completion`s, stat guards, sha check, bak, breaker, abort, hook-throw = crash, `beforeLocalWrite` hook ahead of every graph write), `engine.ts` (`runSync(deps, hooks)`: recover → temp cleanup → scan → delta → plan → conflicts → journal → execute → persist). M7: `session.ts` (`runSyncSession(deps, hooks)` = §3.6 steps 1–2 + 10 around `runSync`: `resolveLayout` with the persisted ids (a changed graph folder resets the state instead of deleting the graph), `SessionLock` acquire → `{kind:'locked', expired}` or run with a 90 s renew loop (TTL 5 min; a failed renewal aborts) → release in `finally`; `flushEditor('before-scan')` right before the scan; `checkRemoteStatus` (D9, read-only, `countRemoteChanges` against `state.remote`); `summarizeRun`/`describeRunProblems`/`describeSkippedOps`/`effectiveDeviceName`), `throttle.ts` (`throttleLatest` for progress). `src/google/mirror.ts` (`createDriveMirror({ client, graphFolderId })`) implements `RemoteMirror` over `DriveClient`; tests run it over `FakeDrive`, never a hand-rolled fake. `tests/sync/world.ts` is the two-device world; `tests/sync/scenario.test.ts` is the randomized DoD fuzz; `tests/sync/session.test.ts` runs the session over the world with the real layout/mirror/lock code.
  - `src/fs/` (M5) is pure TS too: `graphFs.ts` (`GraphFs` interface, `FsError {op,path,code}` + `isFsNotFound`, strict root-relative paths, `fileUrl`), `hostBridgeFs.ts` (`createHostBridgeFs({ root, bridge, fetch })`, the **only** `GraphFs` implementation; the bridge call and the `file://` fetch are injected), `ignore.ts` (plan §3.4 rules + `*.gdsync-tmp`), `scanner.ts` (`scanFiles(fs, { cache })`, re-hash only when size or mtime differs), `atomicWrite.ts` (`writeFileAtomic` via `<dir>/.<name>.gdsync-tmp` + `rename`), `bak.ts` (`createBakSession` → `logseq/bak/gdsync/<YYYYMMDD-HHmmss>/`, `backupCopy`/`moveIn`), `limit.ts` (`mapLimit`), `hash.ts`. `src/logseq/fsHost.ts` is the one place that touches `window.top.apis.doAction` (`hostBridge`, `createHostGraphFs`, `createHostProfileFs`). Tests use `tests/fs/fakeHost.ts`: an emulator of the host's IPC handlers; `createFakeGraphFs()` is the real adapter over it (this is the plan's "FakeGraphFs").
  - `src/google/` has device-code OAuth, the HTTP transport, and the Drive client. It is **host-agnostic** (no `logseq` import): `fetch`, `sleep`, the key-value storage and the credentials resolver are injected by `src/logseq/googleHost.ts`, and tests script `fetch` (`tests/google/helpers.ts`). `GoogleAuth.fetch` is the authorized fetch (Bearer header, one refresh + retry on 401, backoff underneath) that the Drive client builds on. Request bodies must be re-sendable (string/URLSearchParams/Blob/ArrayBuffer), because the transport retries.
  - Drive layer (M4): `drive.ts` (`DriveClient`, `createDriveClient({ fetch })`), `driveQuery.ts` (the `q` grammar), `driveUpload.ts` (multipart ≤ 5 MB, resumable above in 1 MiB chunks), `folderCache.ts`, `layout.ts` (`bootstrapLayout` → plan §3.3 folders; M7: `verifyLayout` (3 `files.get`), `resolveLayout` (verify the persisted ids or bootstrap), `findLayout` (find-only, for the remote check)), `lock.ts` (`.gdsync/lock.json`, acquire/renew/release/break-expired). Every non-2xx is an `HttpError`; `isNotFound(err)` for 404, `InvalidPageTokenError` for a rejected changes token. `tests/google/fakeDrive.ts` is an **HTTP-level** Drive emulator (multipart/resumable parsing, `fields` masks, fault injection); test the client and the M6 engine against it, never against a hand-rolled interface fake.
  - `src/logseq/` and `src/ui/` hold host wiring and the React UI. `src/logseq/syncController.ts` (M7) is the real `SyncController` (`src/sync/controller.ts`): it builds per-run deps (a **fresh Drive client per run**, `createHostGraphFs`, `resolveLayout`/`findLayout`, `createDriveMirror`, `createDriveLock`, `flushEditor` = `Editor.checkEditing()` → `exitEditingMode()` → 1.2 s wait), mirrors `auth.state` into `status`, throttles progress (250 ms), turns `resolveConflicts` into `status.pendingConflicts` + a promise the dialog resolves, maps the run onto `lastSync`/`lastSyncAt`/`lastError` (`expiredLock` → the panel's "Break the lock and sync" → `syncNow({ breakExpiredLock: true })`), aborts a run when `status.graph.path` changes or the session is lost, and `dispose()` (awaited by `beforeunload`) aborts + awaits the run so the lock is released. `backupNow` is an M8 placeholder. The M2 mock (`src/mock/`, `DemoControls`) was deleted in M7.
- UI state flows one way: engine → `Store<SyncStatus>` (`src/sync/store.ts`, `status.ts`) → toolbar (`registerToolbar` re-registers the item on state change), panel (`useStore`), toasts. `deriveSyncState()` is the single source of the five toolbar states. Auth has its own `Store<AuthState>` (`signed-out` | `connecting` | `signed-in`) that the controller mirrors; toasts for auth events live in the controller, never in `src/google/`.
- Google session: one JSON string in `logseq.FileStorage` at `auth/google-session.json` (plaintext). The e-mail comes from Drive `about.get` (`drive.file` carries no identity). `TokenStore.clear()` overwrites the file with `null` rather than deleting it.
- All file I/O goes through `GraphFs` so the bridge can be swapped out if a Logseq update breaks it.

## Non-Obvious Gotchas (verified; details in the reference doc)

- `logseq.Request` bypasses CORS but **JSON-stringifies every request body** on host 0.10.15. It cannot send binary, multipart, or form-urlencoded bodies, so Drive uploads must use iframe `fetch` (Ref §6.7). Plain `fetch` to Google works from the plugin iframe (CORS ok, resumable `Location` header exposed).
- Bridge (`doAction`) failures **resolve with a host-realm `Error` object** instead of rejecting; `Date`s in `stat` results are host-realm too. `instanceof` fails across realms, use `Object.prototype.toString.call(v)` / `getTime()`.
- Bridge `readFile` returns UTF-8 text only; read bytes with `fetch('file://…')` (`fileUrl()` percent-encodes per segment; `encodeURI` breaks on `#`/`?`). `unlink` moves graph files into `logseq/.recycle/` (it really deletes only under `~/.logseq`); use `rename` for our own `logseq/bak/gdsync/` moves. There is no directory delete.
- Bridge handler surfaces differ (verified in the shipped `handler.cljs`): `stat`/`rename`/`mkdir-recur`/`unlink` **resolve** with a host-realm `Error`; `copyFile`/`listdir` are async and **reject** with `Error invoking remote method 'main': …`; **`writeFile` swallows failures** (backup to `logseq/bak/`, error notification, resolves `null`) and does not create parent directories. `HostBridgeFs` normalises all three into `FsError` and always `mkdirp`s first. `listdir` returns absolute paths of every non-directory including dot files; the ignore rules are ours.
- Atomic-write temp files are dot-prefixed (`pages/.Alpha.md.gdsync-tmp`): the host watcher and `readdir` ignore every dot-prefixed segment, so Logseq never indexes a half-written file.
- An external write to the file of the block **being edited** closes the editor and silently drops unsaved input, with no host prompt. Force-save with `logseq.Editor.exitEditingMode()` before scanning or writing.
- `logseq.FileStorage.removeItem`/`clear` are fire-and-forget in the SDK; only `setItem`/`getItem`/`hasItem`/`allKeys` are true round-trips. **`getItem` of a missing key rejects** ("file not existed"); call `hasItem` first (Ref §6.6).
- Google OAuth answers use two error dialects (`{error, error_description}` for OAuth, `{error:{code,message,errors[{reason}]}}` for Drive); `parseGoogleError` in `src/google/errors.ts` reads both and `describeGoogleError` is the only place that turns them into user-facing text. A 403 is retried only for the Drive rate-limit reasons, so the OAuth 403s `slow_down`/`access_denied` reach the poll loop.
- `logseq.updateSettings()` does not update `logseq.settings` synchronously. Read fresh values in `onSettingsChanged` (Ref §5.1).
- Settings (`~/.logseq/settings/<id>.json`) and `logseq.FileStorage` are plaintext on disk, and FileStorage values are strings only (Ref §5.1, §6.6).
- `DB.datascriptQuery` errors can resolve with a `"#lspmsg#error#"` key instead of rejecting (Ref §6.2).
- The plugin main UI is a full overlay; Escape and click-outside closing must be implemented by the plugin (Ref §5.2).
- `showMainUI`/`hideMainUI` emit `ui:visible:changed` **before** they update the state behind `logseq.isMainUIVisible`, so the getter is stale inside the listener. `src/ui/useMainUiVisible.ts` reads `visible` from the event payload instead (Ref §5.2).
- The global `logseq` is typed as the `ILSPluginUser` interface, which lacks the `version` getter of the `LSPluginUser` class. `logseq.version` does not compile; the SDK version is the pinned 0.0.17 anyway.
- `npm audit` reports dompurify (critical) and lodash-es (high) advisories, all transitive under the pinned `@logseq/libs` 0.0.17. They cannot be fixed without breaking the pin (D3); accepted, revisit at M9.
- Settings schema `type: 'button'` does not exist on 0.10.15 (the item is silently not rendered).
- A toolbar item **can** be updated by calling `registerUIItem` again with the same `key` (host `register-plugin-ui-item` replaces the entry; verified in 0.10.15 source). Its wrapper is `div#injected-ui-item-<key>-<pid>`, and it moves into the toolbar "plugins" dropdown (key prefixed `pl-`) once the user has pinned items, so scope injected CSS by your own class names, never by the container.
- Toasts: `UI.showMsg(text, status, { key, timeout: 0 })` is sticky, a second call with the same `key` replaces the toast in place, and `UI.closeMsg(key)` removes it (verified in `logseq/sdk/ui.cljs` + `handler/notification.cljs`). Re-showing with a non-zero timeout schedules an extra auto-clear each time.
- `provideStyle({ key, style })` registers a style only if that key is not already registered (`register-plugin-resources`), so a keyed style cannot be replaced; encode state in the DOM (`data-state`) instead.
- Google OAuth: device-code flow with scope `drive.file` (non-sensitive). The GCP consent screen must be **"In production"**; in "Testing" status, refresh tokens expire after 7 days.
- Drive semantics the client relies on: `appProperties` PATCH merges keys and a `null` value deletes one; `files.update` bodies must not carry `parents`; resumable chunks must be multiples of 256 KiB except the last, a 308 answers with `Range: bytes=0-N` (absent = nothing stored), a lost session is a 404/410; folder `DELETE` cascades; `changes.list` entries report a file's **current** state and may repeat an id. Duplicate names (folders or lock files created in a race) are always resolved to the oldest `createdTime`, then the smallest id, so every device converges on the same one.
- Engine invariants (M6, verified by the fuzz): the changes token is advanced on **every** run because the remote view is persisted next to the base (`state.remote`); a skipped conflict or failed download is re-planned from that view, not re-fetched. Journal recovery folds recorded completions in and **re-plans**, it never replays ops. Drive has no idempotent create: a create whose response was lost and retried leaves a younger identical twin that no device ever addresses again (the oldest wins), so the engine trashes the younger duplicates it meets in a delta. A "keep local" answer stashes the overwritten remote version in `logseq/bak/gdsync/<ts>/` first (`BakSession.stash`). A folder the feed shows as new/renamed/moved/trashed forces a full listing (descendants' paths change without their own feed entries); with a fresh client per run that means **every run after any folder creation, own uploads included**, lists the whole tree once (10 s vs 2.5 s in the M7 E2E; M9 item). Test worlds must use a **ticking clock** (every `now()` +1 ms), otherwise two writes in one tick share an mtime and the scanner's size+mtime cache hides the second one.
- Session facts (M7): the changes token predates a run's own uploads, so the next feed re-reports them; anything that counts "remote changes" must compare against `state.remote` (`countRemoteChanges`). The Drive ids persisted in the state are verified each run (`verifyLayout`); when they stop verifying (root renamed in settings, folder trashed) the state is **reset** before planning, because the old base against an empty new mirror would plan "delete everything locally". Logseq seeds `logseq/config.edn`, `logseq/custom.css` and `pages/contents.md` into a newly added graph, so a "new device" first sync is the both-non-empty merge with add/add conflicts on those three, not the empty-graph mode. `Editor.checkEditing()` and `exitEditingMode()` work on 0.10.15 as typed in SDK 0.0.17.
